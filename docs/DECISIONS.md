## ADR-018：交易资格先于财务风险评分，桌面流式列与手机分行

- 状态：Accepted；日期：2026-10-07；关联CR-023 / DATA-034 / UI-037。

## ADR-015：风险展示共享原生弹窗，先按少量样本接入三页

- 状态：Accepted；日期：2026-10-06；关联CR-020 / DATA-031 / UI-034。
- 用户确认三页接入后明确先看少量样本格式，故停止全量补齐，仅输出9只当前评分；未取得评分的股票显示待核实并可查看原因。保留原始加分算法，不改变风险等级边界，也不自动剔除股票。
- `RiskProvider`只加载一次当前评分字典，三页及历史样本共享`RiskScoreCell`和原生`dialog`详情；弹窗挂载到页面根部，避免宽表/固定列裁切。使用浏览器原生模态焦点和退出键，关闭恢复焦点与背景滚动；风险列放在股票旁，避免新增评分藏在宽表末端。
- 中文转换仅在展示层进行；数据字段及机器等级继续保持稳定，便于复算和兼容旧测试数据。所有窗口内原因/指标/等级均中文，不改变分数和原文证据。
- 不将样本文件接入每日全量自动生成，不更改部署流程。ADR-014的算法与下限决定继续有效，其“仅独立测试页”的展示范围由本次决定替代。

## ADR-014：风险评分先按原始加分实施，缺失输出下限

- 状态：Accepted；日期：2026-10-06；关联CR-019 / DATA-030 / UI-033。
- 用户确认暂不加权，保留四模块原始分便于解释。最终普通累计+组合后应用最高Risk Floor再封顶，不用优质财务抵扣风险；不将模块按理论最大值归一化。
- 三年现金转化为三年累计CFO/累计归母净利，分母≤0不计算；应收与营收同比取同一报告期、收入阈值接近度用TTM，正式年度/预告触发+35单独判断。收入扣除信息缺失且原始收入未低于线时不认定排除触发。净资产以归母权益，短债以短期借款+一年内到期非流动负债；零债务/零利息单独标记，不伪造无限比率。
- 供应商同报告期同披露日重复空指标记录优先保留非空版本，不跨版本填补；后续较新更正缺失仍保留缺失。财报审计供应商字段与内控审计不混用，卓然2025年度采用公司原文覆盖。
- 公告只收录核实样本，二次问询以不同函或明确二次事件识别；同函回复去重。事件保留证据和披露时间，可显式解除；审计意见取最新已公开意见。不对未确认事件设置默认安全值，不将下限低分称CLEAN。
- 仅建立独立测试页与手动生成器；现有股票池、三页生产行为及部署计划不变。原研究提案与附件中的初始加权建议均由本次用户确认覆盖。

## ADR-012：默认筛选后取100只，与全市场250榜分开排名

- 状态：Accepted
- 日期：2026-10-06
- 关联：CR-017 / DATA-028 / UI-031 / OPS-007；替代ADR-011默认展示规则。

固定全市场250名中默认仅4只符合显示条件，无法满足用户至少约50只的阅读需求。用户确认默认先排除北交所和亏损，再取全沪深市场市值最低100只，财报不完整排除，不设置25亿元上限。扫描按原始市值升序，取得100个完整非亏损报告后停止，审计保留此前所有候选的财报状态；不基于原创业板盈利池拼名单，不复用不同截止日的财报结论。

全市场250名作为独立模式保留，双榜分别排名和汇总。筛选后的100排名不能声称全A股排名。默认不出现北交所/亏损按钮，全榜初始显示全部后允许独立隐藏，模式切换重置搜索/分类和市值升序，以免继承隐性筛选只显示几只。同一JSON/时间快照和历史目录覆盖两榜并集，相关数据源读取两榜名单。

## ADR-011：固定250名全市场榜，北交所与亏损独立隐藏

- 状态：Accepted
- 日期：2026-10-06
- 关联：CR-016 / DATA-027 / UI-030 / OPS-006。

用户允许扩大至全市场250名或改为非亏损非北交所100名，选择250名固定总榜，继续保留真实全市场市值排名与两类风险/市场信息。显示开关不能改变源名单，不跨越250名递补；因此默认可见数量随实际财报与市场分布变化，当前快照只有4只。北交所以完整ts_code的.BJ后缀识别，数据缺少ts_code时仅可用明确market名称，禁止按920或旧代码前缀推断交易所。

亏损与北交所过滤独立，交集必须两开关均开启；先统计隐藏北交所，再统计尚未被北交所过滤的亏损股，隐藏数量与可见数量之和等于当前搜索/板块命中数。未知财报不视作亏损。既有固定列、财报入口、活跃度、板块排序、数据路径与兼容路由保留。

## ADR-010：以最新交易日概念强势表现作为可核对的市场优先级

- 状态：Accepted
- 日期：2026-10-06
- 关联：CR-015 / DATA-026 / UI-029。

分类原顺序无热度意义，用户选择近期公告或市场热点优先。采用新浪公开概念行情中的最新交易日涨幅及成交额作为市场表现代理；只在股票已有概念中选取排名前20%且上涨的主题，最多两个，通用属性及未覆盖概念折叠。用前三个领涨股行情取得一致的市场参考日期，日期缺失/不一致/未来或行情不完整则不给热度。当前来源175个有效板块，仅107个名称与269只股票的488种概念精确一致；不做未经核实的跨名合并。

标签称“强势概念”，公开排序方法和参考日，不把单日涨幅当作公告依据、新闻热度或多日持续热点。主体业务相关标签必须已有来源分类且直接匹配业务词组；相似行业和概念不同名时保守不显示，避免把市场归属等同实际业务。

## ADR-009：板块统一分类来源，业务摘要绑定原文

- 状态：Accepted
- 日期：2026-10-05
- 关联：CR-013 / CR-014 / DATA-024 / UI-026 / DATA-025 / UI-027。

用户要求行业和概念，使用新浪财经公司分类页中申万行业及新浪概念，统一来源覆盖沪深北。现有Tushare账户概念接口无权限，东方财富公开接口批量访问不稳定，因此不采用跨来源补齐或从业务猜测概念。分类以当前采集快照为准，独立显示北京时间采集时间，不宣称是行情交易日当时分类；缺失明确提示。仅用板块筛选显示股票，原选股与指标口径不变。

主营业务摘要使用原文中的产品/服务名词，人工词组配置与原文哈希绑定；原文变化不能复用旧词组。未整理的简单业务可提取明确短词组，复杂介绍保留原文并提示待整理。行业/概念与主营业务分列，避免将市场概念当作实际业务。

## ADR-007：最低市值榜先固定名单，再标记亏损和行情缺失

- 状态：Accepted
- 日期：2026-10-05
- 关联：CR-012 / DATA-023 / UI-024 / OPS-005

用户要求全 A 股最低市值100只且显示亏损风险，因此先按原始总市值锁定100只，包含 ST/*ST、北交所及仍在交易的退市整理股票。财报、成交额、波幅或历史长度不影响选股。单股查询失败保留排名并显示空缺，禁止递补成“有完整数据的100只”。

亏损采用最近三年已披露连续完整年度和最新正式累计财报的归母净利润<0；不沿用被替代盈利页的扣非、TTM、现金流门槛。已确认亏损优先显示红色，其他财报缺失同时显示待核实；零利润不算亏损。

活跃度用可解释的60日真实波幅，旁列大幅涨跌天数和日均成交额，不合成分数。须完整覆盖最新61个市场交易日；停牌或短历史不向前延长窗口。股东生成覆盖新100只，原观察名单和匹配逻辑不变。

## ADR-008：每日标准化真实波幅与独立盈利活跃池

- 关联：DATA-020/021、UI-023、OPS-004

## ADR-007：使用有来源的姓名观察名单和前十大流通股东快照

- 状态：Accepted
- 日期：2026-09-18
- 关联需求：DATA-016, UI-020

观察名单由人工公开资料核对维护，不根据单季收益排行自动增删。按精确姓名匹配，保留同名不确定性，不合并关联人或机构账户。首版统一使用前十大流通股东，避免把总股东和流通股东口径混合比较。股东快照非标准十名时保守限制缺席推断；缺失数据明确展示。页面采用共享详情弹窗，股票下方小入口，不新增宽表列。每日既有工作流追加独立生成步骤，行情及财报公式保持不变。

## ADR-001：使用 Tushare 作为当前主要数据源

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：OPS-001, NFR-001

### 背景

项目需要一个可用于个人看板的数据源来获取股票日线数据，并支持后续指标计算与自动化更新。

### 备选方案

1. 聚宽
2. AkShare
3. Tushare

### 决定

当前项目使用 `Tushare` 作为主要数据源。

### 原因

- 历史讨论中曾考虑聚宽，但使用成本较高
- 曾尝试 AkShare，但部分接口稳定性不足
- 当前仓库已经基于 Tushare 实现了现有数据链路

### 后果

- 依赖 Tushare 的权限、额度和服务可用性
- 部分接口可能在未来出现可用性波动
- `TUSHARE_TOKEN` 必须通过安全方式配置
- 不得将 Token 提交到仓库

### 替代关系

无

## ADR-002：52 周高点使用最高成交价 high

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：DATA-003

### 背景

52 周高点的定义会直接影响“距离高点”指标结果。需要统一其金融含义和实现口径。

### 备选方案

1. 使用最近 252 个交易日中的最高 `high`
2. 使用最近 252 个交易日中的最高 `close`
3. 使用全历史最高价

### 决定

使用最近 252 个交易日中的最高成交价 `high`，不使用 `close`。

### 原因

- 市场通常将 52 周高点理解为区间内实际达到过的最高成交价
- 更符合“距离真实高点还有多远”的观察需求

### 后果

- 指标值通常小于或等于 `0`
- 后续任何改为 `close` 的方案都必须走正式变更流程

### 替代关系

无

## ADR-003：主要指标在 Python 层统一计算

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：DATA-001, DATA-002, DATA-003, DATA-004, DATA-006, DATA-007, NFR-001

### 背景

项目需要保证不同页面状态、不同复权模式下的指标口径一致，避免前端多个位置重复拼装公式。

### 备选方案

1. 全部在前端实时计算
2. Python 计算核心指标，前端只负责展示和交互
3. Python 与前端混合计算

### 决定

主要指标在 Python 数据层统一计算，前端以读取结果并展示为主。

### 原因

- 保持公式唯一
- 避免不同前端组件计算结果不一致
- 更利于批量验证和数据排障
- 前端可专注于展示、排序和交互

### 后果

- 数据结构变更需要同步更新 TypeScript 类型
- 前端不应自行重新发明指标公式

### 替代关系

无

## ADR-004：移动端优先的简洁表格设计

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：UI-001, UI-002, UI-003, UI-004, UI-005, NFR-002

### 背景

项目的重要使用场景是在手机上快速扫表，因此布局应优先服务可读性，而不是堆叠尽可能多的信息。

### 备选方案

1. 传统券商终端式高密度布局
2. 移动端优先的简洁表格布局
3. 为移动端和桌面端分别维护完全不同的页面

### 决定

采用移动端优先的简洁表格设计，在统一页面内兼顾桌面端与移动端。

### 原因

- 用户需要经常在手机上扫描股票
- 信息优先级比装饰更重要
- 不采用传统终端式高密度复杂布局

### 后果

- 表格需要支持横向滚动
- 关键列层级和高亮策略必须保持克制
- 如需调整固定列或主布局，需要正式评估移动端影响

### 替代关系

无

## ADR-005：使用 GitHub Actions 和 GitHub Pages

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：OPS-001, OPS-002

### 背景

项目需要低维护成本的自动构建与静态部署方案。

### 备选方案

1. 手工本地构建并上传
2. GitHub Actions + GitHub Pages
3. 迁移到其他托管平台

### 决定

当前使用 GitHub Actions 执行自动构建，并部署到 GitHub Pages。

### 原因

- 成本低
- 与仓库集成简单
- 适合个人项目维护

### 后果

- `schedule` 不保证严格执行时间
- 自动更新失败时，需要通过 Actions 日志排查
- 站点部署方式受 GitHub Pages 子路径规则影响

### 替代关系

无

## ADR-006：正式引入仓库内文档治理体系

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：REQ-001

### 背景

项目要求和历史决策过去主要存在于聊天记录和临时上下文中，难以形成长期可追踪的维护约束。

### 备选方案

1. 继续依赖聊天记录和人工记忆
2. 仅维护 README
3. 在仓库内建立规则、需求、决策、变更和变更日志体系

### 决定

在仓库内建立正式文档治理体系。

### 原因

- 让 AI 与人工维护共享同一事实来源
- 减少口头要求丢失
- 支持需求、变更与实现之间的追溯

### 后果

- 后续维护需要同步更新文档
- 非正式想法不能再直接视为正式需求

### 替代关系

无
