## ADR-001：使用 Tushare 作为当前主要数据源

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：OPS-001, NFR-001

### 背景

项目需要一个可用于个人看板的数据源来获取股票日线数据，并支持后续指标计算与自动化更新。

### 备选方案

1. 聚宽
2. AkShare
3. Tushare

### 决定

当前项目使用 `Tushare` 作为主要数据源。

### 原因

- 历史讨论中曾考虑聚宽，但使用成本较高
- 曾尝试 AkShare，但部分接口稳定性不足
- 当前仓库已经基于 Tushare 实现了现有数据链路

### 后果

- 依赖 Tushare 的权限、额度和服务可用性
- 部分接口可能在未来出现可用性波动
- `TUSHARE_TOKEN` 必须通过安全方式配置
- 不得将 Token 提交到仓库

### 替代关系

无

## ADR-002：52 周高点使用最高成交价 high

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：DATA-003

### 背景

52 周高点的定义会直接影响“距离高点”指标结果。需要统一其金融含义和实现口径。

### 备选方案

1. 使用最近 252 个交易日中的最高 `high`
2. 使用最近 252 个交易日中的最高 `close`
3. 使用全历史最高价

### 决定

使用最近 252 个交易日中的最高成交价 `high`，不使用 `close`。

### 原因

- 市场通常将 52 周高点理解为区间内实际达到过的最高成交价
- 更符合“距离真实高点还有多远”的观察需求

### 后果

- 指标值通常小于或等于 `0`
- 后续任何改为 `close` 的方案都必须走正式变更流程

### 替代关系

无

## ADR-003：主要指标在 Python 层统一计算

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：DATA-001, DATA-002, DATA-003, DATA-004, DATA-006, DATA-007, NFR-001

### 背景

项目需要保证不同页面状态、不同复权模式下的指标口径一致，避免前端多个位置重复拼装公式。

### 备选方案

1. 全部在前端实时计算
2. Python 计算核心指标，前端只负责展示和交互
3. Python 与前端混合计算

### 决定

主要指标在 Python 数据层统一计算，前端以读取结果并展示为主。

### 原因

- 保持公式唯一
- 避免不同前端组件计算结果不一致
- 更利于批量验证和数据排障
- 前端可专注于展示、排序和交互

### 后果

- 数据结构变更需要同步更新 TypeScript 类型
- 前端不应自行重新发明指标公式

### 替代关系

无

## ADR-004：移动端优先的简洁表格设计

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：UI-001, UI-002, UI-003, UI-004, UI-005, NFR-002

### 背景

项目的重要使用场景是在手机上快速扫表，因此布局应优先服务可读性，而不是堆叠尽可能多的信息。

### 备选方案

1. 传统券商终端式高密度布局
2. 移动端优先的简洁表格布局
3. 为移动端和桌面端分别维护完全不同的页面

### 决定

采用移动端优先的简洁表格设计，在统一页面内兼顾桌面端与移动端。

### 原因

- 用户需要经常在手机上扫描股票
- 信息优先级比装饰更重要
- 不采用传统终端式高密度复杂布局

### 后果

- 表格需要支持横向滚动
- 关键列层级和高亮策略必须保持克制
- 如需调整固定列或主布局，需要正式评估移动端影响

### 替代关系

无

## ADR-005：使用 GitHub Actions 和 GitHub Pages

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：OPS-001, OPS-002

### 背景

项目需要低维护成本的自动构建与静态部署方案。

### 备选方案

1. 手工本地构建并上传
2. GitHub Actions + GitHub Pages
3. 迁移到其他托管平台

### 决定

当前使用 GitHub Actions 执行自动构建，并部署到 GitHub Pages。

### 原因

- 成本低
- 与仓库集成简单
- 适合个人项目维护

### 后果

- `schedule` 不保证严格执行时间
- 自动更新失败时，需要通过 Actions 日志排查
- 站点部署方式受 GitHub Pages 子路径规则影响

### 替代关系

无

## ADR-006：正式引入仓库内文档治理体系

- 状态：Accepted
- 日期：2026-07-22
- 关联需求：REQ-001

### 背景

项目要求和历史决策过去主要存在于聊天记录和临时上下文中，难以形成长期可追踪的维护约束。

### 备选方案

1. 继续依赖聊天记录和人工记忆
2. 仅维护 README
3. 在仓库内建立规则、需求、决策、变更和变更日志体系

### 决定

在仓库内建立正式文档治理体系。

### 原因

- 让 AI 与人工维护共享同一事实来源
- 减少口头要求丢失
- 支持需求、变更与实现之间的追溯

### 后果

- 后续维护需要同步更新文档
- 非正式想法不能再直接视为正式需求

### 替代关系

无
